# 运行记录与旧项目迁移

仅在编写赛题代码、运行失败或升级旧 runner 时加载。这里是 Standard 的运行一致性检查，不是操作系统沙箱。

## 当前运行契约（1.1）

统一从项目根目录执行：

```bash
python paper_output/code/modeling/run_modeling.py --timeout-seconds 600
```

- `--timeout-seconds` 是每问的正数墙钟时间上限，默认 600 秒。实际求解较久时明确调大；它与求解器自己的 `time_limit` 不同，不保证限时内找到解。
- 开始执行前原子写入 `RUNNING`，全部结束才写入 `PASS` 或 `FAIL`。异常、中断、超时或子问题失败后不保留旧 `PASS`。
- 每次执行给每问分配唯一 `run_id`，通过 `MATHMODEL_RUN_ID` 环境变量交给赛题脚本。使用 `result_contract_io.execution_provenance(...)` 或 `upsert_question_contracts(...)` 自动记录它；不能复制旧记录或自行编造 ID。
- 自定义结果写入器须把当前环境的 ID 写入 `execution_provenance.run_id`，并设置 `execution_schema_version: "1.1"`。每问至少登记一个真实、非空的输出文件。
- 零退出码但没有当前 ID 的结果也失败。确定性计算可以得到相同数值和字节，但必须真实重新执行并产生本次来源记录。
- 每问输出必须是项目内相对路径；拒绝绝对路径、`..` 和指向项目外的链接。所有路线问题须恰好被本次运行覆盖一次；后续问题不能覆盖前面问题的输出。
- 运行结束记录 `model_results.json`、`metrics.json`、`conclusions.json`、`table_index.json` 四份共享契约的 SHA-256。其后手改数值、结论或索引会在 S6 被拦截，不仅在 S7 检查。
- 同一项目只允许一个 runner 同时执行。第二次启动直接失败，不覆盖正在运行的账本；进程退出后系统释放锁，遗留锁文件无需删除。

## 日志与失败处理

完整标准输出和错误写入 `paper_output/results/run_logs/<run-id>.log`，账本只保留最后约 4000 字节，不把全部日志加载到内存。日志可能持续增长，长期实验应自行归档；不要记录密钥。

超时后终止当前问题及同一进程树的子进程，记录 `timed_out`、退出码 124 和日志位置。Windows 使用 `taskkill /T`，POSIX 使用独立进程组。脱离进程树的守护进程、恶意程序及外部服务不在此保证内；正式赛题代码不得启动后台常驻进程。

出现失败时：查看账本和日志，修复赛题代码或输入，再重新运行统一入口。不能手改 `run_manifest.json` 使其变绿，也不清空旧结果假装新计算已完成。保留旧文件用于排查，但失败账本不允许正式写作。

独立运行 `q*_model.py` 只用于调试，不能更新正式运行账本。确认正确后仍须运行统一入口，再通过 S6、S7 和 S8。

## 旧项目

1. 备份赛题代码和计算结果；不要覆盖已有人工代码。
2. 生成器只更新仍带 managed marker 的文件。已手改 runner/helper 需对照新模板人工迁移，或在独立新项目重新生成。
3. 同时更新 runner 与 `result_contract_io.py`，使结果来源带当前运行 ID；使用自定义写入器时同步迁移。
4. 重新计算，再生成证据门禁、写作计划和最终文档。新来源记录不能搭配 1.0 账本。

兼容读取旧 1.0 账本，但 S6 会明确警告：它没有本次执行 ID 和共享结果快照，不具备本节的完整保证。不能通过把版本字段改为 1.0 绕过新记录的检查。

## 保证边界

这些检查防止常见旧结果复用、误改和失败状态混淆，不证明建模正确，也不能防御拥有目录写权限的程序伪造整套证据。结果哈希一致但指标口径写错，仍由 S7 的 CSV、单位、样本范围和论文逐句绑定检查拦截。
