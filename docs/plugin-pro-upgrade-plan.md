# MathModel Plugin：基于 Pro 的集成与质量升级计划

日期：2026-09-10。状态：实施前设计记录。当前 Alpha 已完成的功能与实际验证见 [实施报告](./plugin-upgrade-validation.md)；真实赛题对照验收尚未完成。

目标：用户安装一次，在 Codex 对话里完成比赛。插件将 Pro 的指导、执行、证据和交接组织成可恢复的工作流；让新的会话理解已经做出的建模判断，并能可靠地继续计算和写作。右侧页面辅助查看实际状态。

本轮交付是基线核对、架构决策、实施顺序和验收标准。文中的拟建模块、版本和指标均为计划，不代表当前插件已经具备这些能力。

## 1. 明确比较基线

已通过 `git ls-remote` 核对远端 Pro 分支。比较基线锁定为：

- Pro：`3.3.0-pro.1`，提交 `da520d49c62c8f5dc3755eb16bedefd78e77b466`。
- 插件已提交基线：`cbd6c75b2c52b15841316bb091697980792c426d`，插件 `0.3.0`。
- 工作区另有未提交的 `0.3.1` 输入索引改动；不是已经发布的新基线。
- 当前插件携带 Standard `2.3.0`，使用 S0–S8、`paper_output/` 和 Standard Guard。Pro 使用 P0–P9、`paper_output_pro/` 和 Pro 检查点/门禁。当前插件尚未达到 Pro 等价能力。

Pro 已经包含三路独立审题、每问默认四条路线、预注册比较规则、真实运行回执、独立复算、至少十个随机种子、敏感性/压力/消融、三次用户确认、证据冻结、双向结论映射、五角色独立审稿和 Word/PDF 检查。这些全部是继承基线，不作为插件新增宣传。

Pro 也已有阶段记忆和前向赛题验收要求。因此，本方案比较的是恢复信息的完整性、执行可靠性、可执行验证范围和实际论文表现，而不是有没有 memory 文件、多少个 Skill 或多少个审稿角色。

来源：固定提交的 [Pro README](https://github.com/yushui2022/MathModel-Skill/blob/da520d49c62c8f5dc3755eb16bedefd78e77b466/README.md)、[Pro 契约](https://github.com/yushui2022/MathModel-Skill/blob/da520d49c62c8f5dc3755eb16bedefd78e77b466/docs/pro-contracts.md)、[前向验收要求](https://github.com/yushui2022/MathModel-Skill/blob/da520d49c62c8f5dc3755eb16bedefd78e77b466/docs/forward-evaluation.md)。

## 2. 用户体验与范围

用户在比赛项目中说“开始建模”后，入口识别实际项目与版本，检查环境，给出简短的题目/阶段摘要，随后按 Pro 流程推进。只有需要打开证据、比较结果时才展示右侧页面。

正常任务保留 Pro 的三个确认点：题意和论文范围、模型路线、结果与不确定性。插件把确认内容组织成具体、可审阅的结果，记录真实用户决定与批准对象的哈希；不把泛泛的“继续”当成对变化后对象的批准，也不额外重复请求已经有效的批准。

典型交互应包括：

| 用户表达 | 预期行为 |
|---|---|
| “开始建模” | 从实际文件和当前契约判定新建/恢复，使用唯一 Pro 总入口 |
| “继续第二问” | 恢复第二问的目标、假设、路线和未完成任务，先检查它依赖的第一问结果是否仍有效 |
| “刚才为什么没选随机森林？” | 指向该项目的路线淘汰理由和对应证据；没有记录则明确未知 |
| “这批计算跑到哪里了？” | 给出真实完成/失败/运行中的实验，附日志和种子，不从聊天推测 |
| “第二问数据改了” | 列出受影响的计算、结论和章节，生成修复次序，保留原版本记录 |
| “这句话的数字从哪来？” | 从正文结论定位指标、实验回执、代码和输入版本 |
| “准备交付” | 执行最新 Pro 门禁与新增适用检查，输出正式文件及尚未解决的问题 |

本阶段不做本地 IDE、账号/计费、云协作或自动提交比赛论文。不以插件数量、模型角色数、页数增加作为质量升级。界面采用中文、中性色、窄面板优先，避免继续扩建空状态看板。

## 3. 相对 Pro 的五项实质升级

| 升级 | Pro 已有 | 本插件拟增加的可观察行为 | 比赛价值 |
|---|---|---|---|
| 按问题恢复上下文 | 阶段、下一步、检查点、哈希和失败摘要 | 自动聚合当前问题的已确认假设、选模理由、被淘汰路线、有效结果、未决异议和写作断点 | 新会话接着做，不重新解释整场比赛 |
| 可恢复任务与角色交接 | 同步实验脚本，真实回执，评审准备/收集契约 | 持久任务队列、真实执行归属、日志游标、停止与恢复；宿主角色执行记录的收集与核验 | 关闭界面、换会话后不丢实验，不把仍在运行的任务当成失败 |
| 可执行的数学规格检查 | 数值复算及文本式验证要求 | 首先独立重算线性/整数优化的目标、约束和整数性；后续检查声明的预测切分和数据处理记录 | 抓住“程序跑完，但数学问题解错”的具体错误 |
| 修改影响与必要重算 | 哈希变化后批准和下游门禁失效，已有结论/证据映射 | 把输入、实验、指标、结论、章节连接起来，解释失效原因并列出重算队列 | 改一问时知道哪些需要重做，避免无关计算重复执行 |
| 干净环境重放 | 记录当前 Python、依赖、命令和输入输出 | 生成可移交的重放清单、依赖锁、输入版本和独立重放报告 | 队友或新环境能复算论文中的关键结果 |

真实赛题对照测试是上述升级的证明方式，不单独算“新增功能”。

## 4. 架构与源码决策

采用一个安装包、一个正式工作流核心、一个项目运行服务。正式核心以 Pro 为基础，不在同一项目内同时激活 Standard 和 Pro 总入口。

```text
用户对话
  → 插件入口：绑定比赛项目、恢复上下文
  → Pro 总入口：判断阶段、路由专业 Skill、组织用户确认
  → 专业 Skill：审题/选模/实现/验证/写作/审稿
       ↔ 持久项目契约：问题、路线、实验、结论、论文版本
       ↔ 项目运行服务：任务、日志、状态读取、文件索引
             ↑ CLI / MCP / 可选右侧页面共用
```

具体决策：

1. 在 `feat/codex-plugin` 分支受控引入固定 Pro 基线的规范源码、依赖、同步脚本和测试。导入前列出差异，不把两个版本的 Skills 简单并集。
2. 保持 `packages/claude/.claude/skills` 为本分支规范 Skill 源，经 Codex 平台转换后生成插件。插件专属入口与运行适配单独维护；不直接编辑安装缓存或其他生成 Skill 副本。
3. 用构建清单记录 `core_edition/core_version/source_commit/plugin_version/contract_schema`。插件版本与 Pro 工作流版本分开记录。
4. `paper_output_pro/` 继续作为正式成果和 Pro 契约根；`.mathmodel/` 保存服务/队列/可重建索引。不能把 SQLite 中的“成功”当作论文门禁通过。
5. 新增恢复和影响索引使用独立 schema 与派生状态，不随便修改 Pro schema `3.3`。需要增加正式门禁或变更批准范围时，另作兼容性迁移并重测。
6. 旧 Standard 项目仍由原版运行。可识别并展示迁移说明，不把 S8 PASS 转换为 Pro PASS；已有 Pro 项目绑定的安装版本改变后按其哈希契约重新核验。
7. Standard/Pro 现有 ZIP 分发保留。插件分支的 Pro 改动不自动推到 `standard` 或 `pro`。原 Standard 回归保留独立、锁定基线的 CI 任务，不能为适配 Pro 而删除旧测试断言。

官方支持把相关 Skills 组合成一个插件，MCP 与 UI 可选；按需加载本来就是 Skill 的能力。这里的插件设计利用统一分发与工具接入，不宣称扩大模型上下文或改变模型参数。[官方插件架构](https://developers.openai.com/plugins/concepts/plugins)、[官方 Skill 加载机制](https://learn.chatgpt.com/docs/build-skills)。

## 5. Skill 设计：保留职责，补交接，按需展开

不追求多拆几十个 Skills。沿用 Pro 的职责边界，首先增强已有 Skill，再决定是否有独立发现的必要。

| 模块 | 职责及本次调整 |
|---|---|
| `mathmodel-plugin-entry` | 负责定位项目/运行环境、取得恢复包并交给 Pro 总入口；不另写一套选模流程 |
| `pro-workflow-orchestrator` | 唯一 P0–P9 决策入口；根据阶段、前置条件、有效批准及问题依赖决定动作 |
| `problem-doc-model-selector` | 保留三路独立审题与共识；增加稳定的问题/假设标识和依赖关系 |
| `pro-model-tournament` | 保留默认路线数、七维评分和预注册比较；按题型读取所需参考，而不是一次读完整模型百科 |
| 数据获取与数据处理 Skills | 保留来源核验；输出单位、字段含义、数据处理与切分的可检查记录 |
| `model-code-and-result-generator` | 输出关联题目/路线/输入版本的 run-spec；通过受控执行器产生真实回执 |
| `quality-assurance-auditor` | 整合新的优化/预测检查器；根据适用性报告具体违规，不能把未知视为通过 |
| `paper-formal-writer` | 保留逐问论证与唯一正式源稿；恢复具体章节断点，按影响报告修订已失效结论 |
| `pro-review-board` | 保留五个真实隔离角色；绑定实际宿主执行记录，正确处理同版评审的中断和重试 |
| `context-memory-keeper` | 从“记录阶段”增强为按任务聚合项目语义；摘要必须能返回原始契约位置 |

增加机器可读的 Skill 路由清单：稳定 skill ID、职责、适用阶段、前置契约、输出契约、完成检查和失败回路。清单是可执行工具的定位/路由数据，不是一份重复的长提示词。

每次交接生成简短任务包，包含 `task_id/question_ids/skill_id/input_revision/input_refs/expected_outputs/acceptance_checks/next_on_failure`。Skill 接收结果时重新核对输入版本。过期任务的结果保存为历史，不覆盖新版本结果。

Pro 当前 P0 要求审计全部 Skill 指令，不能以“渐进加载”为由偷偷省略。第一步保留该要求；后续把公共执行规则抽成较小的共享契约，阶段细节移入明确引用的 references，再验证覆盖与冲突检查等价。主流程不为每个阶段重复灌入全部知识。

多个 Skill 不等于多个 Agent。独立审题/复算/审稿由 Codex 实际可用的隔离上下文能力执行；插件脚本不创建另一套隐藏模型服务，不自动购买或消耗独立 API 额度。宿主能力不足时报告缺口，不能用角色标签冒充隔离执行。

## 6. 升级一：能解释判断的恢复包

重做 `build_context_packet.py`，其职责是从有效项目契约生成视图，不再只排列文件名和阶段号。

| 内容 | 主要来源与校验 |
|---|---|
| 项目身份、核心版本、交付范围 | `pro_config.json`、实际安装清单、当前项目路径 |
| 当前小问、任务边界、依赖 | `problem_consensus.json` 与新增问题依赖索引 |
| 已确认假设及变更原因 | 共识、批准对象和追加的决策记录；不编造缺失理由 |
| 选中/备用/淘汰路线 | `candidate_routes.json`、`tournament_report.json` |
| 有效实验、失败实验、当前运行 | 真实 run receipts、任务所有者、环境/输入哈希 |
| 关键结果及可引用范围 | `claim_evidence_map.json`、冻结证据与适用检查结果 |
| 已写章节和待修订问题 | `paper_plan.json`、当前源稿定位、审稿 findings |
| 下一动作及所需 Skill | Pro 状态评估和待完成任务，而不是手填 current_phase |

默认恢复包控制为可读的短摘要（目标不超过约 8,000 字符），按当前小问优先；其余内容有明确的分页/引用入口和省略说明。该上限只限制恢复摘要，不限制建模推理、任务总量或论文篇幅。

派生摘要每条关键事实带源文件、JSON 定位或正文锚点、源哈希和状态。来源变化时不能继续作为已确认事实。默认读取不写 QA、memory 或数据库；显式 `refresh_context` 才持久化快照，失败返回真实错误。

验收：P2/P5/P7/P8 中断后，由没有旧对话的新会话恢复，正确指出当前问题、选模理由、有效结果和未决问题；不接受别的项目的记忆，不重复已完成且仍有效的计算。代码测试检查恢复信息完整性，真实新会话测试检查是否真的会使用。

## 7. 升级二：计算与角色任务可恢复

将 `workbench.py` 的状态读取、执行器、进程管理拆开。每个项目只有一个修改状态的运行服务；MCP 和页面连接该服务，不各自创建执行器。服务描述符包含项目身份、实际端口、进程身份与健康检查信息。

任务状态分为 `queued/running/succeeded/failed/cancelled/interrupted/unknown`；验证状态独立为 `not_checked/pass/fail/stale`。进程退出码为 0 只表示计算成功退出。

数据库原子领取任务。幂等键覆盖项目、任务类型、规范化参数、代码/数据/环境版本和 seed。同一逻辑提交复用 job ID；用户要求独立重复实验时明确产生新的 attempt/run ID。重试不能覆盖历史回执。

第一版仍限制一个项目同一时刻一个会修改共享结果的任务；随机种子可排队。隔离 run 目录和原子聚合通过测试后再开放并行计算，不以并行数作为升级指标。日志流式写入有容量限制的文件，用游标增量读取。

客户端关闭不停止任务。服务重启时先核验执行所有者、进程创建时间和已有回执；不能凭 PID 或新建客户端就宣布任务失败。不可安全恢复的任务显示 interrupted，保存日志后新建重试，不假称能从任意求解器内部断点恢复。

独立角色任务由主 Codex 使用宿主提供的能力发起，记录宿主实际返回的 ID、输入快照、输出和完成状态。完成记录用于核验五角色是否审阅同一版本。没有宿主能力时不伪造调用或认证；同用户可写的文件不是防篡改证明。

验收：十个种子中第四个运行时关闭页面并换会话，最终有十个有效唯一回执；重启服务后已完成三个不重复执行。停止有子进程的实验后取消终态保持不变且无遗留子进程。打开第二个 MCP 客户端不能改变正在运行的实验状态。

## 8. 升级三：首先做能落地的数学检查

第一批仅支持声明为线性规划/混合整数线性规划的优化题。给定冻结数据构造规范问题规格，明确变量、单位、上下界、整数域、目标系数、约束矩阵、右端项与容差。规格绑定题意和路线；从自然语言到规格的正确性仍由审题/数学评审负责。

规格、容差及检查适用性必须在检查点 2 批准前确定，并成为批准对象的哈希依赖。计算后修改约束、目标或容差，会使对应批准和下游结果失效，不能通过放宽规格让既有错误结果过检。M3 明确包含这项契约版本迁移、旧项目诊断和门禁回归；不在兼容层静默添加新的批准含义。

独立验证器直接读取规格和求解结果，重算目标值、每条约束残差、上下界违约和整数性；输出最大违约量与具体约束 ID，不能调用求解脚本自己输出的 feasibility=true 代替检查。

区分可行、已证最优、近似/启发式和未知。LP/MILP 的最优性声明需相应求解器证据、上下界/gap 或适用的证书；验证器没有证书时只报告自己检查到的范围，不能因为多个算法一致便宣布最优。

后续扩到预测题：对显式记录的数据处理流程检查训练/测试样本重叠、时间顺序、声明的特征可用时间与只在训练集拟合的处理步骤。无法检查的任意自定义预处理标记未覆盖，不宣称自动发现所有形式的数据泄漏。

新增检查在其声明适用范围内进入正式交付门禁。题型不适用与验证缺失必须区分，不能靠改题型标签绕过失败。不能普遍要求任何建模题都编码成线性规划。

验收：固定注入超容量、整数变量出现小数、目标值记错、没有依据却标最优等错误，支持范围内全部检出并给定位；合法可行解通过其对应检查。预测扩展覆盖样本交叉、未来字段和错误拟合范围。检查器与被检算法不共享决定正确性的实现。

## 9. 升级四：把失效变成可处理的修改清单

从现有 Pro 哈希、回执和结论映射派生有向依赖图：

`输入/假设 → 数据处理 → 模型/实验 → 指标/图表 → claim → 正文章节 → 冻结与终审`

节点具有稳定 ID、所属小问和当前内容哈希；边记录依赖类别及来源。没有完整依赖声明时采用保守失效，不能为了省计算漏掉潜在影响。

用户改变第二问专用输入时，输出受影响实验/结论/段落、依赖路径和建议修复顺序。第一问若被第二问共享则照常纳入；第三问独立且输入/实现/环境不变的历史回执先保留，并经现行规则核验后复用。

这里的“必要重算”只节省计算，不跳过 Pro 的批准范围、全量冻结和最终五角色同版审稿。审批对象变了仍需按 Pro 重新批准。最小重算无法证明时宁可扩大核验范围。

验收：为包含跨问题依赖的项目建立期望影响集合；变更专用输入、共享工具函数和单纯措辞时，分别得到正确影响集合。无关计算不重新运行，但相关批准和论文检查仍正确失效。

## 10. 升级五：可移交的重放交付

在 `paper_output_pro/delivery/` 生成重放清单和归档，包含声明依赖锁、解释器/求解器版本、允许分发的输入快照或校验定位、计算脚本、种子、已批准比较规则和重放命令。排除会话令牌、缓存、用户凭据及没有分发授权的材料。

输入不允许打包时，清单明确需要用户提供的原件与哈希；不能把不可取得的数据描述为开箱即用。商业求解器/本机依赖缺失时给出诊断，不自动购买服务。

在新的比赛目录与干净环境执行 replay，生成独立的运行与比较报告，保留原证据清单用于比对。不能把原项目绑定的批准复制过去伪装新项目完成 Pro 审批。

为此定义独立的重放执行模式：只执行冻结清单声明且哈希匹配的脚本、输入及参数，输出“重放一致性报告”，不授予新项目任何 Pro 阶段通过。正式建模 runner 继续要求当前项目有效的检查点 2；重放器不伪造批准，也不提供跳过正式 runner 检查的通用开关。修改输入或继续建模必须回到正式工作流。

验收：空白目录、清洁 venv 复算关键结论，并满足原定容差或统计等价规则；缺依赖/缺输入明确失败。旧冻结包内容保持不变。能跑通重放也不等同于数学模型本身正确。

## 11. CLI、MCP 和右侧页面

统一核心先提供 CLI，MCP 使用相同函数与状态，网页只读相同数据并提交受控任务。第一阶段不新增前端框架或 Node 安装要求。

拟保留/扩展的接口：

| 接口 | 约束 |
|---|---|
| `doctor/open_workspace` | 识别实际安装版本/解释器/项目；返回经过健康检查的服务地址 |
| `get_context_packet/get_next_action` | 按 question/task 过滤；返回事实来源、真实阻塞与 Skill 定位，不启动隐藏 Agent |
| `get_status/list_artifacts/read_artifact` | 有版本与游标；区分文本、科学图表、PDF 和二进制附件 |
| `run_job/get_job/cancel_job` | 类型与参数 schema 固定；使用规范 run-spec，不接收任意 shell 字符串 |
| `get_change_impact` | 返回影响图与修复建议，不自动授予批准 |
| `prepare_review/collect_review` | 源稿版本和真实宿主角色执行记录绑定；准备操作只生成待执行任务 |
| `export_replay` | 生成可审阅清单后按已授权范围打包，明确未包含的输入 |

脚本路径始终根据实际插件根定位，项目路径显式传入；不依赖 `${...}` 是否在宿主中恰好插值。若宿主无法可靠解析安装路径，首次准备生成本机可用配置并做实际协议测试。通用依赖和本机配置放在可写运行目录；缓存中的插件代码保持只读。

本地服务强制回环监听、校验 Host/Origin 与会话令牌、在读取前检查解析后的目录边界和 symlink/junction。静态资源同样不能通过路径拼接访问插件外文件。默认不用网页承载任意 HTML/SVG 代码执行。

右侧页面优先呈现：当前小问、尚未解决的问题、实际运行、结论证据和交付状态。支持查看日志、停止实验、复制恢复摘要和预览实际结果；在窄面板中保留这些关键动作。官方浏览器面板是主要展示路径；MCP Apps 能力须宿主检测，不把 ChatGPT 的 UI 能力视为 Codex 已保证能力。

## 13. 发布验收：能证明什么才宣传什么

### 工程必过项

- 包在只读安装缓存，比赛目录有中文和空格且无项目级 `.agents/skills`：从发行物实际配置启动 MCP initialize/tools/list、读取上下文、预检、运行和格式检查。
- 两项目、多个 MCP/浏览器客户端并存：无串写、不抢夺任务归属、无虚假运行地址。
- Guard 只读查询不修改 QA 文件或全局进程 cwd；损坏记忆、跨项目记忆、失效哈希给出明确诊断。
- 大日志用流式限额和分页；取消与失败保留回执；SQLite/快照版本随文件和运行变化推进，事件导出能分页读全。
- 无令牌、恶意 Host/Origin、静态路径穿越、编码/反斜杠变体、祖先 junction/symlink 越界读取被拒绝。
- ZIP verify 比较逐文件内容、版本和构建清单；改同名文件或篡改归档必须失败；相同源码两次构建字节一致。
- 保留原有适用回归和确定性构建检查；新增 Pro、真实 MCP 协议、安装、任务故障、阶段恢复和数学错误注入测试。
- 不使用用户比赛原目录跑破坏性故障测试；新环境、依赖、运行产物和浏览器测试文件统一落在 G 盘，超过 500 MB 先检查空间。

### 对照设计

先做一题真实历史多问优化赛题试点，对比 A：原 Pro、B：仅接入 Pro 的插件、C：带新增能力的插件。B 用来区分“包装效果”和实际功能增益。各组使用同一模型/推理档位、输入、任务范围和预定资源条件，隔离项目与对话；不跨组复用论文、结果或审批。

在 P2/P5/P7/P8 设置恢复检查，其中至少一次使用没有旧对话的新会话。设定的故障点包括中途重启、变更一个专用输入和暂停一个实验。前向比较中每组的必要用户批准均真实记录；额外澄清记录数量和原因，不把跳过批准当成效率提升。

试点之后按 Pro 原有预测、优化、图、公开数据四类验收；计划每类至少三组成对 A/C 独立运行，共 24 次正式运行。该数量是评测计划，不代表本轮已启动计算或自动消耗账户额度。不同模型单独报告，不能把一个模型的表现外推到所有 Codex 模型。

每批开始前固定观察窗口、资源预算和失败处理规则。全部预登记运行进入主比较，不能只统计完成论文：窗口内未产生符合交付门禁的论文记为未完成，主评分计 0，同时单独报告完整交付率、失败原因及已完成论文的条件均分。插件的完整交付率不得低于原 Pro；不得通过延长单组运行时间或删除失败样本达到质量目标。

| 指标 | 计划验收目标 |
|---|---|
| 错误晋级/过期证据接受 | 固定故障案例为 0；人工事件和旧 memory 不能授予通过 |
| 冷启动恢复 | 固定场景的问题/阶段/依赖选择全部正确；真实场景逐例记录遗漏和误路由 |
| 无必要的重复计算 | 固定不变输入恢复场景为 0；真实比赛报告重复任务数与原因 |
| 数学错误注入 | 已声明支持的错误类别全部检出，合法控制例不误报 |
| 论文硬性质量 | 不出现未解决 Critical/Major、虚构结论或不新鲜的交付门禁 |
| 论文盲评 | 使用预先确定的量表：数学与题意 25、实验验证 25、证据正确性 20、逐问论证 20、表达一致性 10；目标均分比原 Pro 提高至少 5 分且数学/证据维度不下降 |
| 使用成本 | 记录输入上下文量、恢复时间、实际重算时间、失败恢复次数、额外用户干预；有实际 token 数据才报告 token 节省 |

论文比较应由不知道组别的独立评阅者完成；人工评阅由用户指定评阅者，自动角色评审另列，不能替代人工证据。重复运行展示离散程度，不用小样本宣称统计显著或保证获奖。

如果论文评分未改善、但恢复和重复计算明显改善，只宣传“恢复/执行效率升级”。若仅安装改善，则只宣传集成便利。出现质量退步则不能升级为稳定版。所有失败保留，不只展示最好的论文。

## 14. 已发现的实际风险与处理

以下来自本轮静态代码审查；不等于已经动态复现或修复。

| 当前缺口 | 风险与处理 |
|---|---|
| `JobRunner.__init__` 无条件把 running 改 failed，MCP/页面各创建 Runner | M0 必须单项目单所有者与原子领取；优先于任何 UI/新 Skill |
| Guard 通过进程全局 `os.chdir()` 调用 | 多项目解析可能混乱；改为显式 root 的纯查询/隔离子进程 |
| `format_check` 路径指向项目中不存在的通用脚本位置；MCP 依赖相对启动路径 | 统一活动安装的解析器与 doctor，从发行 ZIP 验证真实配置 |
| context 默认读取会写数据库/快照；`--write` 吞掉刷新错误 | 拆纯读取与显式刷新，错误传播，按源哈希核验记忆 |
| 静态资源路径无 containment；缺少 Host/Origin 校验，允许非回环 host 参数 | 先修边界后再扩大可预览文件范围 |
| 日志结束后才读取，取消状态会被完成回调覆盖 | 流式写入与终态规则；进程树取消和重启故障测试 |
| 构建 verify 只比文件名 | 改逐字节/哈希校验、manifest 校验与真实解包安装测试 |
| Pro P0 指令全量审计与按需上下文存在张力 | 先保持 Pro 语义；公共规则抽取后单独论证等价，不能直接省略审计 |
| 哈希校验可能全部通过但模型数学定义有误 | 独立问题解释、规格核对、可执行数学检查和盲评共同验证 |
| 自动最小重算遗漏未声明依赖 | 依赖不完整时保守扩大失效，终审保持全量 |
| 干净环境重放受商业求解器与输入授权影响 | 明确支持矩阵、所需依赖和无法随包分发的输入，不伪造“一键复现” |

## 15. 第一个开发批次

第一批只完成 M0 与 M1 的安装/核心适配基础，并准备 M2 的恢复 schema。先让发行物在独立比赛目录运行正确的 Pro 核心；之后实现一题优化赛题的按问恢复、持久任务和约束检查，作为第一条完整使用路径。

第一次可展示成果应是：用户换到全新对话，说“继续第二问”，系统能说明已选模型及理由、仍有效的实验、剩余问题和确切下一步；运行后能指出真实的约束违例或通过的检查范围，并把新结论正确交给论文写作。

这条路径通过之前，不继续以装饰性界面、更多角色名称或新增空白状态页作为项目进度。
